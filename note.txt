Category 2: Technical / Hardware Diagnostics
Q1: TROUBLE SHOOT NOT POSTING?

If a system won’t POST, it means it’s failing before the OS even loads, so I focus on core hardware. I’d reduce to a minimal boot configuration, check POST indicators like beep codes or LEDs, reseat components, and then swap in known-good parts to isolate the failure.


Q2: SERVER IS REBOOTING UNDER LOAD, DIAGNOSE:
I would start by reviewing the system event logs and dmesg output to look for kernel panics, hardware faults, or thermal warnings around the time of each reboot. Unexpected reboots under load typically point to a few likely causes: thermal shutdowns, insufficient or unstable power delivery from the PSU, or faulty memory.
To narrow it down, I’d run a memory stress test using MemTest86 to rule out RAM issues, while also monitoring CPU and GPU temperatures under load to check for overheating. In parallel, I’d verify that the power supply is properly rated for the system’s actual power draw and not operating near its limits.
Finally, I’d document each reboot in context—load conditions, temperatures, and system uptime—to identify any consistent patterns before drawing conclusions.

- hardware + firmware feature of a system that lets you turn on using another device with 'magic packet'

BIOS (Basic Input/Output System):
- cpu executes BIOS -> hardware init/POST -> find boot devices -> load OS (bootloader)
- load the bootloader from disk (first thing to run, loads the OS kernel into RAM)
- stored in ROM (old), now flash memory (not read-only)

why firmware on motherboard? - because system needs bare minimum set of instructions with resources like an os, RAM, drivers. Nothing is guarenteed to work yet, so we put it always reachable with zero setup

ROM vs Flash Memory:
- both non-volatile (keeps data without power)
- ROM permanently written at factory, can't be changed (bugs can't be fixed, no support for new hardware)
- Flash memory can be rewritten (firmware flashing are BIOS/UEFI updates), so hardware compatibility updates. 
	It's EEPROM, used in SSDs, USB drives, BIOS/UEFI chips.

5. Drivers / Runtime (CUDA, NCCL, Docker)
4. Operating System
	- involved: kernel, device enumeration, drivers
	- common: device shows in BIOS but not OS, kernel errors, Disk/network not recognized
	- tools: lshw, demesg, journalctl -xe (kernel messages, system services (Docker, SSH, CUDA drivers)), lsblk
3. Firmware / BIOS
	- involved: PCIe config, memory config, CPU features, Boot settings
	- common: Devices disabled, PCIe bifurcation wrong 
	- tools: IPMI, BIOS
2. Hardware Topology (PCIe, NUMA, wiring)
	- involved: PCIe lanes and slots, NUMA layout, GPU<->CPU placement, riser cables
	- common: GPU not detected, GPU running x8 not x16, intermittent device fails, wrong CPU<->GPU pairing
	- tools: lspci, lsusb, nvidia-smi topo -m (NVLink, NIC->GPU under same PCIe Switch and node), numactl --hardware
	
1. Physical Hardware (power, thermals, components)
	- involved: PSU, cables, CPUs, RAM, GPUs, Cooling
	- common: loose seating(DIMM), overheating, random shutdowns, system not powering on
	- signals: NO POST, Fans spin but no display (black screen)
	- tools: IPMI, reseat or swap parts, lspci, memtest86+, ipimitool, smartctl

	Plug hdmi into gpu not motherboard
	Deug lights, reseat the components, clear the cmos
	bios update

-> fans spin, but immediately shut off in a loop
	usually ram issue or unstable bios, clear cmos

-> Display but no windows
	boot priority windows drive needs to be first, if not listed at all reseat or might be corrupt
	Drive is there but won't boot, do windows installation usb and repair

-> bare minimum works, that means something was shorting it
-> bare minimum doesn't work, 4 core components need to be swapped

SERVER SYSTEM CRASHING UNDER LOAD:
1. Confirm Crash
	- service failure, kernel panic, resource exhaustion 
	- maybe cpu unresponsive and server isn't truly dead
	- ping <server_ip> (doesn't work -> deeper kernel or hardware issue) (works-> ssh or user-space level)
2. Check Logs 
	- system logs: sudo journalctl -xb (kernel, disk i/o, out of memory, failed services)
	- if 'systemd' logs don't help, check log files: sudo less (/var/log/messsages, syslog, kern.log)
3. Identify Kernel Panic or Hardware issues
	- memtest, disk check 
4. Check Resource usage Trends 
	- free -h, df -h
